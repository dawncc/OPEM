# 工具调用的功能画像与近似聚合

## 设计目标

工具调用不能只按工具名归档。同一功能可能由 `Bash`、`shell`、`exec`、浏览器或 MCP 工具完成；同一个通用执行器也可能承载搜索、测试、文件修改等完全不同的任务。

OPEM 因此将一次调用表示为可解释的使用画像：

- 标准化操作：从结构化参数或包装命令中识别实际操作；
- 功能类别：搜索、文件、测试、版本控制、浏览器、网络、数据库、记忆、文档、图像、协作、代码和命令执行；
- 使用标签：从输入与输出中按加权词频提取关键词；
- 语言信号：根据扩展名、命令和代码特征识别 Python、TypeScript、SQL、Shell 等语言；
- 近似度：组合功能类别、标准操作、工具名、关键词 Jaccard 和语言 Jaccard，形成 0–100% 的可解释分数。

聚类先要求功能类别一致，再按加权近似度归并。搜索、测试等语义明确的类别允许跨工具名聚合；通用 Shell 和未知工具采用更高阈值，降低误合并风险。

## 性能策略

工具画像使用版本化的 `_tool_profile_v2` 元数据缓存：新调用在归档写入时计算，历史调用在服务启动时一次性回填。页面请求只读取缓存，不再重复扫描完整输入和输出；升级画像规则时修改版本即可触发安全重建。

聚合查询延迟加载大文本字段，并通过单次批量查询只取首屏需要的 2,000 字符输入和 4,000 字符输出预览。相似度聚类先按“功能类别 + 标准动作”缩小候选集合，避免在无关工具间进行两两比较。

## 业界方法与取舍

1. [Gorilla](https://arxiv.org/abs/2305.15334) 将每个 API 文档作为独立文档建立检索，并比较 BM25、GPT Index 等检索器，证明检索能帮助模型适应变化中的 API，但检索质量不足也可能损害结果。
2. [ToolLLM / ToolBench](https://arxiv.org/abs/2307.16789) 为 16,000 多个 API 建立类别和使用任务，并使用神经 API Retriever 从大工具集合中推荐相关工具。
3. [Tool2Vec](https://arxiv.org/abs/2409.02141) 从真实使用方式学习工具表示，并提出 retrieve-then-refine 与多标签分类；这说明调用输入和输出是比静态工具名称更有价值的信号。
4. [LlamaIndex ObjectIndex](https://docs.llamaindex.ai/en/v0.10.19/examples/objects/object_index.html) 将工具及其元数据序列化为可检索对象，可在向量索引上做相似度 Top-K；其分层检索实践也强调结构化元数据过滤和语义检索结合。
5. [OpenTelemetry GenAI Semantic Conventions](https://github.com/open-telemetry/semantic-conventions-genai) 为工具调用的名称、参数、结果和追踪关系建立统一语义属性，说明原始字段应保留，分类标签应作为派生层而非替换原始记录。

当前实现选择“规则分类 + 使用画像 + 加权 Jaccard”，因为它无需 LLM、embedding 或数据库迁移，符合本地部署与可审计要求。后续启用 embedding 时，可以保持功能类别与元数据过滤不变，仅把近似度层替换为向量余弦相似度和重排器。

## 页面使用

工具页默认显示功能聚合视图，并提供以下组合过滤：

- 状态；
- 功能类别；
- 编程或数据语言；
- 输入/输出关键词标签；
- 最低组内近似度；
- 原始文本关键词。

每个聚合组显示参与工具、功能动作、关键词、语言、近似度、成功/失败数量和时间范围；展开后仍可查看完整输入、输出与来源会话。
